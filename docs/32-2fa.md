# 32 — Two-Factor Authentication (TOTP / Google Authenticator)

OpenWA can require a **time-based one-time code** (TOTP — Google Authenticator, Authy, 1Password, …) in
addition to an API key when signing in to the dashboard. It is **opt-in per API key** and available to
**admin keys** only.

## The model: enrolled keys are interactive-only

The dashboard authenticates with a raw API key sent on every request, and that same key type is used by
headless clients (curl, the MCP mount, integrations). A login-only code prompt would be pointless — an
attacker with a stolen key would just call the API directly. So 2FA here is **enforced server-side with
a session**:

- When you enable 2FA on a key, that key becomes **interactive-only**. The API guard **refuses it as a
  plain bearer credential** unless a short-lived, post-code **dashboard session token** accompanies it.
- At each dashboard login you enter your key, then a 6-digit code; the server verifies the code and
  issues the session token, which the dashboard sends alongside the key from then on.
- A stolen enrolled key is therefore **useless without the current code** — and it can no longer be used
  headlessly at all.

> **Keep a separate operator key for automation.** Because an enrolled key stops working for headless
> API clients, do NOT enable 2FA on a key your scripts/integrations use. Create a second `operator` key
> for automation and reserve the 2FA-protected `admin` key for the dashboard.

## Enabling 2FA

1. Sign in to the dashboard with an **admin** key and open **API Keys**.
2. In the **Two-Factor Authentication** panel, click **Enable 2FA**.
3. Scan the QR code with your authenticator app (or type the shown key in manually).
4. Enter the 6-digit code to confirm. 2FA is now on for this key; your current session stays logged in.

From the next login, entering the key prompts for a code before the dashboard opens.

## Disabling 2FA

In the same panel, click **Disable 2FA** and enter a **current** code (a step-up check, so a stolen
session alone can't turn it off).

## Server configuration

Both are optional and backend-only.

| Env                  | Default    | Meaning                                                                  |
| -------------------- | ---------- | ------------------------------------------------------------------------ |
| `MFA_KEY`            | _(auto)_   | Server master secret (32 bytes, base64 or hex). See below.               |
| `MFA_SESSION_TTL_MS` | `43200000` | Lifetime of a post-code dashboard session before a new code is required. |

### `MFA_KEY` — the server master secret

`MFA_KEY` encrypts each key's stored TOTP secret (AES-256-GCM) and signs the dashboard session tokens
(HMAC). You do **not** need to set it on a single machine: OpenWA generates a random key and persists it
to **`data/.mfa-key`** (owner-only, `0600`) on first use.

Set it explicitly (32 random bytes, base64 or hex — e.g. `openssl rand -base64 32`) when:

- you run **multiple nodes** behind a load balancer — all nodes must share the same `MFA_KEY`, or a
  session minted on one node won't verify on another; the per-node file won't match.

Changing `MFA_KEY` invalidates existing enrollments (users must re-enroll) and outstanding sessions.

## Recovery — a lost authenticator device

If the **only** admin key has 2FA enabled and its device is lost, you are locked out of both the
dashboard and the API (the enrolled key is refused everywhere without a code). Recover from the host,
which has access to the data volume:

```bash
# In the OpenWA container / on the host with the repo:
npm run mfa:reset -- --list          # show which keys have 2FA enabled
npm run mfa:reset -- <apiKeyId>      # disable 2FA on one key
npm run mfa:reset -- --all           # disable 2FA on every key
# compiled image: npm run mfa:reset:prod -- <args>
```

This clears the 2FA state directly on `data/main.sqlite`, and the key authenticates normally again.

> **Best practice:** keep a **second admin key without 2FA**, stored securely offline, as a break-glass
> credential so you never depend solely on the host CLI.

## What's stored, and where

- The TOTP secret is stored **encrypted** (AES-256-GCM, keyed by `MFA_KEY`) in the `mfaSecret` column of
  the `api_keys` row — never in plaintext, and never returned by the API after enrollment.
- The dashboard session token is **stateless** (a signed, expiring token) — there is no server session
  table to manage.
- Audit rows are written for `mfa_enrolled`, `mfa_verified`, `mfa_failed`, and `mfa_disabled` (visible in
  **Logs**).
